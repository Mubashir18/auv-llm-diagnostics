# Project 2600: Role B (Diagnostic Agent), Prototype Status

**Project:** LLM solutions for anomaly diagnostics and recommendations in dynamic underwater AUV networks based on log analysis
**Scope of this note:** standalone prototype of the diagnostic agent (Role B), built and tested on synthetic data, before integration with the simulator and the monitoring agent (Role A).
**Status date:** 2026-10-12

---

## 1. Summary

- A working end-to-end prototype exists: synthetic AUV logs -> monitoring summary -> RAG + local LLM -> structured JSON diagnosis -> automatic evaluation.
- On a fresh synthetic test set (n = 40, never used for tuning) the LLM pipeline reached **97.5 % accuracy (39/40)** with **0 % false positives** and **0 invalid outputs**.
- A **tuned threshold baseline reached 100 %** on the same data. On this synthetic benchmark the LLM therefore shows **no detection-accuracy advantage** over a well-tuned rule. Its value has to be argued on other grounds (explanations, recommendations, ease of adding new faults), which are still to be measured.
- Three concrete findings about the Role A / Role B interface came out of the experiments (section 6).
- Everything so far is on **synthetic data generated by us**. Results say that the pipeline works and where it is fragile, not what accuracy will be on Stonefish/ArduSub logs.

## 2. Pipeline

```
[Simulator / synthetic generator]   raw telemetry (CSV now, MAVLink later)
              |
              v
[Role A: Monitoring agent]          window statistics -> short text + key numbers (JSON)
              |
              v
[Role B: Diagnostic agent]          prompt = system rules + reference documents (RAG) + summary
              |                     local LLM (Mistral 7B via Ollama, temperature 0, JSON mode)
              v
JSON diagnosis                      anomaly, confidence, evidence, recommendation
              |
              v
[Evaluation]                        accuracy, false positive rate, confusion matrix, baseline
```

**Stack:** Python 3.11, Ollama (Mistral 7B, 4.4 GB), ChromaDB, pandas/numpy.
**Hardware:** laptop with Intel Core i7-8550U, 16 GB RAM, no discrete GPU. Inference runs on CPU, about 35-50 s per diagnosis.

## 3. Interface between Role A and Role B (proposal)

One JSON file per time window. Both text and numbers are included: the text is easy for the LLM to read, the numbers are computed by code and are reliable.

```json
{
  "id": "s016",
  "window": {"baseline": "t=0-9s", "current": "t=50-59s"},
  "summary": "Thruster 2 RPM changed from 1492 to 612 (-59%). Other thrusters are within normal range. Heading changed by +19.4 degrees. ...",
  "facts": {
    "thruster_rpm_change_pct": {"t1": 0.7, "t2": -59.0, "t3": 0.3, "t4": -0.3},
    "heading_change_deg": 19.4,
    "depth_change_m": 1.39,
    "pos_error_start_m": 1.22, "pos_error_end_m": 1.2,
    "packet_loss_start_pct": 1.4, "packet_loss_end_pct": 1.2,
    "latency_start_ms": 141, "latency_end_ms": 151
  }
}
```

The diagnostic agent returns:

```json
{"anomaly": "propulsion_failure", "confidence": "high",
 "evidence": "Thruster 2 RPM changed from 1492 to 612 (-59%).",
 "recommendation": "Reduce speed and switch to reduced-thrust mode; ..."}
```

Allowed `anomaly` values: `none`, `propulsion_failure`, `navigation_drift`, `communication_anomaly`.
The exact field names will have to be aligned with the real MAVLink fields once the simulation team defines them.

## 4. Experimental setup

| Set | Purpose | Scenarios | Notes |
|---|---|---|---|
| Easy (`s`) | smoke test | 60 (12 evaluated) | large, clean anomalies |
| Dev (`h`) | development and tuning | 40 (10 per class) | mild/late anomalies, higher noise, harder normal logs |
| Test (`t`) | final check | 40 (10 per class) | same generator as dev, different seed; not used for any tuning |

Each scenario is a 60-second log. The monitoring summary compares the first 10 s (baseline) with the last 10 s (current window). Labels are kept separate from the LLM input.
Anomaly types: single thruster failure, navigation (position) drift, communication degradation (packet loss + latency), plus a "none" class.

**Protocol note.** Errors on the dev set were inspected and two principled fixes were made (see 6.1). After that, `src/` was frozen and the test set was run once. The numbers on the dev set are therefore optimistic; the test-set numbers are the ones to quote.

## 5. Results

n = 40 per set. FPR = share of normal logs diagnosed as faulty.

| System | Dev (`h`) acc. | Test (`t`) acc. | Test FPR |
|---|---|---|---|
| Hand-set threshold rule (our first guess of thresholds) | 70 % | 65 % | 0 % |
| Hand-set rule, "increase-based" variant (tuning script) | 62.5 % | 57.5 % | 0 % |
| **Tuned threshold rule** (tuned on dev only) | **100 %** | **100 %** | 0 % |
| **LLM pipeline (Mistral 7B + RAG)** | 95 % | **97.5 %** | 0 % |

- LLM on test: 39/40 correct, approx. 95 % confidence interval 87 % to 99.6 % (small n).
- Invalid or retried JSON outputs on test: 0.
- Average time per diagnosis: 44 s (CPU only).
- First LLM run on the dev set (before the fix in 6.1): 80 % accuracy and 60 % false positive rate. After the fix: 95 % and 0 %.

**Reading of the results.** The tuned rule is at least as good as the LLM on this benchmark, mainly because Role A already condenses the log into clean start/end numbers and the synthetic anomalies have a clear signature. The earlier "LLM 97.5 % vs baseline 65 %" comparison would have been misleading, because the hand-set thresholds were not tuned. A tuned rule also needs labelled data and re-tuning for every new fault type or noise level.

## 6. Findings

### 6.1 Role B accuracy depends on the wording produced by Role A
The first dev run had 6 false alarms on "hard" normal logs. The summary said "Communication degraded: packet loss rose from 5.3 % to 5.3 %", because the monitoring rule triggered on the absolute level (> 5 %), not on a change. The LLM trusted the text. After changing the rule to trigger on a *change*, and clarifying in the reference document that a few percent of packet loss can be normal, false positives dropped to 0 %.
**Proposal:** words like "degraded" or "rose" must only appear when there was an actual change; Role A and Role B should agree on thresholds together.

### 6.2 When text and numbers contradict, the LLM follows the text
Test scenario `t021` (navigation drift, onset at t = 46 s): the facts showed position error rising from 1.38 m to 2.71 m (+1.33 m), but the text said "Position error is stable", because the text rule needs more than +2 m. The LLM answered "none"; the tuned rule, which uses the numbers directly, was correct.
**Proposal:** generate the text and the facts from the same thresholds, and/or tell the LLM explicitly to trust the numbers when they disagree with the text. (Not changed yet, so that the test set stays clean. To be re-measured on a new test set.)

### 6.3 Very late onset is not detectable with a 10-second window
All three LLM errors on dev/test (`h022`, `h026`, `t021`) are slow navigation drifts that started 9-14 s before the end of the log. The position error is still in the range of normal noise. A trend (slope) feature in Role A could help.

### 6.4 RAG is currently not selective
The default Chroma embedding returned the same two documents for every summary (the summaries share almost identical sentence structure, and the embedding does not capture numeric magnitude). With only four short reference documents, all four are now always put into the prompt. So at present RAG acts as a fixed knowledge block rather than as retrieval. The actual contribution of RAG has not been measured yet (see section 8).

### 6.5 Output format needs a worked example
With rules only ("the answer must contain keys X, Y, Z") the model often left out `recommendation`. Showing one filled-in JSON example in the system prompt fixed this: 0 invalid outputs on 40 + 40 + 12 runs. The example may bias the model toward its own label; no such bias was seen so far.

## 7. Limitations

- All data is synthetic and generated with our own assumptions (numbers such as 1500 RPM or the noise level are invented). It is not Stonefish/ArduSub data.
- Dev and test come from the same generator, so the test checks against over-fitting, not against a change of data distribution.
- n = 40 per set, one run each, one model. Confidence intervals are wide.
- Single-fault scenarios only; no combined faults.
- CPU-only inference; a full evaluation of 40 scenarios takes about 30 min.
- Reference documents were written by us from general domain knowledge, not yet reviewed against the AURA/UROSA literature mentioned in the passport.

## 8. Next steps

1. **RAG ablation** on the test protocol: all four documents vs two vs no documents (rules only).
2. **Distribution-shift test set** (new seed, different noise level, different anomaly sizes) for both the LLM and the tuned rule.
3. **Combined faults** (e.g. propulsion + navigation): needs a multi-label or "primary fault + secondary" output format.
4. Agree the **interface and thresholds with Role A** (section 3 and findings 6.1, 6.2) and with the simulation team (real log fields, how communication faults are injected).
5. Evaluate the **quality of explanations/recommendations** (the passport asks for a report-quality methodology), where the LLM should differ from a threshold rule.
6. Run on real **Stonefish/ArduSub logs** as soon as they are available; this is the only test that matters for the 80 % target.
7. Repository, README, Docker instructions, demo video, Extended Abstract.

## 9. Questions for the consultant and the team
