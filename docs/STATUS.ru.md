# Проект 2600: Роль B (диагностический агент), состояние прототипа

**Проект:** LLM-решения для диагностики аномалий и выдачи рекомендаций в динамических подводных сетях АНПА на основе анализа логов
**Назначение документа:** автономный прототип диагностического агента (Роль B), созданный и протестированный на синтетических данных до интеграции с симулятором и агентом мониторинга (Роль A).
**Дата:** 2026-10-12

---

## 1. Краткое резюме

- Создан работающий сквозной прототип: синтетические логи АНПА -> сводка мониторинга -> RAG + локальная LLM -> структурированный JSON-диагноз -> автоматическая оценка.
- На новом синтетическом тестовом наборе (n = 40, ни разу не использовался для настройки) LLM-конвейер показал **точность 97,5 % (39/40)**, **0 % ложных срабатываний** и **0 некорректных ответов**.
- **Настроенный пороговый базовый метод показал 100 %** на тех же данных. Таким образом, на этом синтетическом бенчмарке LLM **не даёт преимущества по точности обнаружения** по сравнению с хорошо настроенным правилом. Ценность LLM нужно обосновывать другими аспектами (объяснения, рекомендации, простота добавления новых неисправностей), которые ещё предстоит измерить.
- В ходе экспериментов получены три конкретных вывода об интерфейсе Роль A / Роль B (раздел 6).
- Все результаты получены на **синтетических данных, сгенерированных нами**. Они показывают, что конвейер работает и где он уязвим, но не позволяют судить о точности на логах Stonefish/ArduSub.

## 2. Конвейер

```
[Симулятор / синтетический генератор]   исходная телеметрия (сейчас CSV, позже MAVLink)
              |
              v
[Роль A: агент мониторинга]             статистика по окну -> короткий текст + ключевые числа (JSON)
              |
              v
[Роль B: диагностический агент]         промпт = системные правила + справочные документы (RAG) + сводка
              |                         локальная LLM (Mistral 7B через Ollama, temperature 0, режим JSON)
              v
JSON-диагноз                            anomaly, confidence, evidence, recommendation
              |
              v
[Оценка]                                точность, доля ложных срабатываний, матрица ошибок, базовый метод
```

**Стек:** Python 3.11, Ollama (Mistral 7B, 4,4 ГБ), ChromaDB, pandas/numpy.
**Оборудование:** ноутбук с Intel Core i7-8550U, 16 ГБ ОЗУ, без дискретной видеокарты. Вывод модели выполняется на CPU, около 35-50 с на один диагноз.

## 3. Интерфейс между Ролью A и Ролью B (предложение)

Один JSON-файл на каждое временное окно. Включены и текст, и числа: текст LLM читает легко, числа вычисляются кодом и надёжны.

```json
{
  "id": "s016",
  "window": {"baseline": "t=0-9s", "current": "t=50-59s"},
  "summary": "Thruster 2 RPM changed from 1492 to 612 (-59%). Other thrusters are within normal range. Heading changed by +19.4 degrees. ...",
  "facts": {
    "thruster_rpm_change_pct": {"t1": 0.7, "t2": -59.0, "t3": 0.3, "t4": -0.3},
    "heading_change_deg": 19.4,
    "depth_change_m": 1.39,
    "pos_error_start_m": 1.22, "pos_error_end_m": 1.2,
    "packet_loss_start_pct": 1.4, "packet_loss_end_pct": 1.2,
    "latency_start_ms": 141, "latency_end_ms": 151
  }
}
```

Диагностический агент возвращает:

```json
{"anomaly": "propulsion_failure", "confidence": "high",
 "evidence": "Thruster 2 RPM changed from 1492 to 612 (-59%).",
 "recommendation": "Reduce speed and switch to reduced-thrust mode; ..."}
```

Допустимые значения `anomaly`: `none`, `propulsion_failure`, `navigation_drift`, `communication_anomaly`.
Точные имена полей необходимо будет согласовать с реальными полями MAVLink, когда команда симуляции их определит.

## 4. Организация эксперимента

| Набор | Назначение | Сценарии | Примечания |
|---|---|---|---|
| Простой (`s`) | проверка работоспособности | 60 (оценено 12) | крупные, чёткие аномалии |
| Разработка (`h`) | разработка и настройка | 40 (по 10 на класс) | слабые/поздние аномалии, больше шума, более сложные нормальные логи |
| Тест (`t`) | итоговая проверка | 40 (по 10 на класс) | тот же генератор, другой seed; не использовался ни для какой настройки |

Каждый сценарий — лог длиной 60 секунд. Сводка мониторинга сравнивает первые 10 с (базовый уровень) с последними 10 с (текущее окно). Метки хранятся отдельно от входа LLM.
Типы аномалий: отказ одного движителя, дрейф навигации (ошибка позиции), деградация связи (потери пакетов + задержка) и класс «none».

**Примечание к протоколу.** Ошибки на наборе для разработки были изучены, внесены два обоснованных исправления (см. 6.1). После этого `src/` был зафиксирован, а тестовый набор запущен один раз. Поэтому результаты на наборе для разработки оптимистичны; цитировать следует результаты тестового набора.

## 5. Результаты

n = 40 на набор. FPR — доля нормальных логов, диагностированных как неисправные.

| Система | Точность (разработка, `h`) | Точность (тест, `t`) | FPR на тесте |
|---|---|---|---|
| Пороговое правило с заданными вручную порогами (наша первая прикидка) | 70 % | 65 % | 0 % |
| То же правило, вариант «по приращению» (скрипт настройки) | 62,5 % | 57,5 % | 0 % |
| **Настроенное пороговое правило** (настройка только на наборе разработки) | **100 %** | **100 %** | 0 % |
| **LLM-конвейер (Mistral 7B + RAG)** | 95 % | **97,5 %** | 0 % |

- LLM на тесте: 39/40 верно, приблизительный 95 % доверительный интервал от 87 % до 99,6 % (малое n).
- Некорректных или повторно запрошенных JSON-ответов на тесте: 0.
- Среднее время на один диагноз: 44 с (только CPU).
- Первый запуск LLM на наборе разработки (до исправления из 6.1): точность 80 % и 60 % ложных срабатываний. После исправления: 95 % и 0 %.

**Интерпретация.** Настроенное правило не хуже LLM на этом бенчмарке, главным образом потому, что Роль A уже сжимает лог в чистые начальные/конечные числа, а синтетические аномалии имеют чёткую сигнатуру. Сравнение «LLM 97,5 % против базового метода 65 %» ввело бы в заблуждение, поскольку пороги, заданные вручную, не были настроены. Кроме того, настроенному правилу нужны размеченные данные и повторная настройка для каждого нового типа неисправности или уровня шума.

## 6. Выводы

### 6.1 Точность Роли B зависит от формулировок, которые выдаёт Роль A
Первый запуск на наборе разработки дал 6 ложных тревог на «сложных» нормальных логах. Сводка гласила: «Communication degraded: packet loss rose from 5.3 % to 5.3 %», поскольку правило мониторинга срабатывало по абсолютному уровню (> 5 %), а не по изменению. LLM доверилась тексту. После перевода правила на срабатывание по *изменению* и уточнения в справочном документе, что несколько процентов потерь пакетов могут быть нормой, ложные срабатывания упали до 0 %.
**Предложение:** слова вроде «degraded» или «rose» должны появляться только при реальном изменении; Роли A и B должны согласовывать пороги совместно.

### 6.2 При противоречии между текстом и числами LLM следует тексту
Тестовый сценарий `t021` (дрейф навигации, начало при t = 46 с): факты показывали рост ошибки позиции с 1,38 м до 2,71 м (+1,33 м), но текст гласил «Position error is stable», так как текстовое правило требует более +2 м. LLM ответила «none»; настроенное правило, использующее числа напрямую, ответило верно.
**Предложение:** формировать текст и факты по одним и тем же порогам и/или явно указывать LLM доверять числам при расхождении с текстом. (Пока не изменено, чтобы тестовый набор остался «чистым». Подлежит повторному измерению на новом тестовом наборе.)

### 6.3 Очень позднее начало аномалии не обнаруживается 10-секундным окном
Все три ошибки LLM на наборах разработки/теста (`h022`, `h026`, `t021`) — медленные дрейфы навигации, начавшиеся за 9-14 с до конца лога. Ошибка позиции всё ещё находится в диапазоне нормального шума. Признак тренда (наклона) в Роли A мог бы помочь.

### 6.4 RAG сейчас не является селективным
Стандартные эмбеддинги Chroma возвращали одни и те же два документа для каждой сводки (сводки имеют почти одинаковую структуру предложений, а эмбеддинг не отражает величину чисел). При наличии всего четырёх коротких справочных документов все четыре теперь всегда помещаются в промпт. То есть в настоящее время RAG работает как фиксированный блок знаний, а не как поиск. Реальный вклад RAG пока не измерен (см. раздел 8).

### 6.5 Формату вывода нужен разобранный пример
При одних правилах («ответ должен содержать ключи X, Y, Z») модель часто пропускала `recommendation`. Один заполненный JSON-пример в системном промпте это исправил: 0 некорректных ответов в запусках 40 + 40 + 12. Пример может смещать модель в сторону своей метки; такого смещения пока не наблюдалось.

## 7. Ограничения

- Все данные синтетические и сгенерированы по нашим собственным допущениям (числа вроде 1500 RPM или уровень шума придуманы). Это не данные Stonefish/ArduSub.
- Наборы разработки и теста получены одним генератором, поэтому тест проверяет отсутствие переобучения, но не смену распределения данных.
- n = 40 на набор, по одному запуску, одна модель. Доверительные интервалы широкие.
- Только сценарии с одной неисправностью; комбинированных нет.
- Вывод только на CPU; полная оценка 40 сценариев занимает около 30 мин.
- Справочные документы написаны нами на основе общих знаний предметной области и пока не сверены с литературой AURA/UROSA, упомянутой в паспорте проекта.

## 8. Следующие шаги

1. **Абляция RAG** по тому же протоколу теста: все четыре документа / два / без документов (только правила).
2. **Тестовый набор со сдвигом распределения** (новый seed, другой уровень шума, другие размеры аномалий) для LLM и настроенного правила.
3. **Комбинированные неисправности** (например, движитель + навигация): нужен формат вывода с несколькими метками или «основная + вторичная неисправность».
4. Согласовать **интерфейс и пороги с Ролью A** (раздел 3 и выводы 6.1, 6.2) и с командой симуляции (реальные поля логов, способ внесения аномалий связи).
5. Оценить **качество объяснений и рекомендаций** (паспорт требует методику оценки качества отчётов), где LLM должна отличаться от порогового правила.
6. Запуск на реальных **логах Stonefish/ArduSub** сразу, как они будут доступны; это единственный тест, значимый для целевого показателя 80 %.
7. Репозиторий, README, инструкция по Docker, демо-видео, расширенная аннотация (Extended Abstract).
